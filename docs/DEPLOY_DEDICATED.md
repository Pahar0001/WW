# Vela на выделенном сервере

Порядок развёртывания на своей машине с российским доменом: приложение,
база и файлы — всё на одном сервере, без зарубежных сервисов.

Это не то же самое, что `docs/DEPLOY_RU.md` и `docs/DEPLOY_FREE.md`: там Vela
живёт на Render, база — там же в Render Postgres. Здесь всё своё.

## Зачем переезд

| Было | Стало |
|---|---|
| База в Render Postgres (США) | PostgreSQL на этом же сервере, том `vela_pgdata` |
| Файлы на диске Render (пропадают при перезапуске) | том `vela_uploads`, переживает перезапуск |
| Приложение на Render | Docker на своей машине |
| Домен зашит в код | берётся из `DOMAIN` в `.env` |

Причин две.

**Сайт засыпает.** Бесплатный тариф Render останавливает сервис после
пятнадцати минут без запросов. Первый посетитель после паузы ждёт около
минуты — браузер к этому времени обычно сдаётся, и человек видит, что сайт
не открывается. Проверено 12 августа 2026: запрос к `velatrips.ru`
не отвечал 25 секунд, а после прогрева тот же адрес отдавал страницу
за 1,1 секунды. Своя машина не засыпает.

**Данные.** У сервиса российские пользователи, и их персональные данные
должны храниться в России: 152-ФЗ, статья 18, часть 5. Пока база в Render
Postgres в США, это требование не выполняется — так и записано
в `docs/PROJECT_HANDOFF.md`, §14.B. Переезд закрывает этот пункт.

Заодно уходит третья мелочь: 16-мегабайтное видео первого экрана сейчас
едет из США через Cloudflare. С сервера в России оно приезжает заметно быстрее.

---

## Что понадобится

- сервер с Ubuntu 24.04, публичным IP и root-доступом;
- минимум **2 ГБ памяти** (Next.js собирается тяжелее, чем работает) и 20 ГБ диска;
- **датацентр в России** — иначе переезд не закрывает 152-ФЗ, ради которого затевался;
- домен;
- ничего больше: репозиторий публичный, ключи для `git clone` не нужны.

---

## Короткий путь: два скрипта

Порядок построен так, чтобы работающий сайт не падал ни на минуту:
сначала новый сервер поднимается рядом со старым и проверяется по IP,
и только потом на него переводится домен.

**Шаг 1 — сервер.** В панели хостинга: Ubuntu 24.04, от 2 ГБ памяти,
российская площадка. Свой SSH-ключ лучше добавить сразу при создании —
пароль root, присланный письмом, стоит потом отключить.

```sh
ssh root@IP-сервера

curl -fsSL https://raw.githubusercontent.com/Pahar0001/WW/main/deploy/bootstrap-vdsina.sh \
  | sh -s -- ваш-домен.ru почта@example.ru
```

Скрипт обновит систему, добавит 4 ГБ подкачки, поставит Docker, закроет
лишние порты, заберёт код в `/opt/vela`, придумает пароли и соберёт стек
**без Caddy**. Сборка идёт 10–20 минут. В конце он покажет адрес вида
`http://IP:8080` и пароль администратора.

Домен в этот момент по-прежнему работает на старой площадке — посетители
ничего не замечают.

**Шаг 2 — секреты и данные.**

```sh
cd /opt/vela
nano .env                       # перенести ключи с прежней площадки, см. раздел 8
./deploy/migrate-from-render.sh "<External Database URL из панели Render>"
```

Открыть `http://IP:8080` и убедиться, что сайт живой, а аккаунты и маршруты
на месте.

**Шаг 3 — домен.** Переключить A-записи `@` и `www` на IP сервера.
У `velatrips.ru` они сейчас ведут на Render (`216.24.57.8` и `.9`), а сама
зона обслуживается `ns1.hosting.reg.ru` — значит, править записи нужно
в панели reg.ru, в управлении DNS-зоной.

**Шаг 4 — включить домен.**

```sh
cd /opt/vela && ./deploy/go-live.sh
```

Скрипт сам проверит, что домен уже приведён на этот сервер, и откажется
работать, если нет: Let's Encrypt считает неудачные попытки и после пяти
за час перестаёт отвечать домену на несколько часов. Дальше он поднимет
Caddy, дождётся сертификата, прогонит проверки и закроет порт 8080.

Разделы ниже описывают то же самое вручную — на случай, если что-то пошло
не так и нужно разобраться по шагам.

---

## 1. DNS

Две записи типа **A**, обе на IP сервера:

```
@     →  IP
www   →  IP
```

Проверить: `ping ваш-домен.ru` должен отвечать вашим адресом. Записи
расходятся от нескольких минут до часа. **Пока они не разошлись, дальше
идти нет смысла**: Caddy не сможет выпустить сертификат.

## 2. Подготовка сервера

```sh
ssh root@IP-сервера

apt update && apt upgrade -y

# подкачка: на 2 ГБ памяти сборка фронтенда может не уместиться
fallocate -l 4G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab

curl -fsSL https://get.docker.com | sh
```

## 3. Код и настройки

```sh
mkdir -p /opt/vela && cd /opt/vela
git clone https://github.com/Pahar0001/WW.git .

cp .env.prod.example .env
nano .env
```

Заполнить обязательно:

| Переменная | Чем заполнить |
|---|---|
| `DOMAIN` | домен без `https://` и без косой черты |
| `ACME_EMAIL` | почта для уведомлений от Let's Encrypt |
| `POSTGRES_PASSWORD` | `openssl rand -base64 24` |
| `JWT_SECRET` | `openssl rand -hex 32` |
| `APP_URL` | `https://` + ваш домен |
| `SUPERADMIN_EMAIL`, `SUPERADMIN_PASSWORD` | первый администратор |

Остальное можно оставить пустым: почта, ИИ-консультант и внешнее хранилище
файлов необязательны, без них сервис работает.

## 4. Запуск

Если домен ещё работает на прежней площадке, поднимайте стек **без Caddy** —
с надстройкой `deploy/docker-compose.check.yml`, которая открывает сайт
по адресу `IP:8080`:

```sh
docker compose -f docker-compose.prod.yml -f deploy/docker-compose.check.yml \
  up -d --build db backend web
```

Когда A-записи уже приведены на этот сервер — обычным способом, тогда Caddy
сразу выпустит сертификат:

```sh
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml ps
```

Первая сборка занимает 10–20 минут: собираются два образа. Дальше:

1. поднимается `db` и ждёт готовности;
2. `backend` создаёт схему (`prisma db push`), наполняет справочники и стартует;
3. `web` поднимает Next.js;
4. `caddy` выпускает сертификат — на это уходит до минуты.

Смотреть, что происходит:

```sh
docker compose -f docker-compose.prod.yml logs -f caddy
docker compose -f docker-compose.prod.yml logs -f backend
```

## 5. Проверка

```sh
curl -s -o /dev/null -w '%{http_code}\n' https://ваш-домен.ru/
curl -s -o /dev/null -w '%{http_code}\n' https://ваш-домен.ru/api/health
curl -s https://ваш-домен.ru/robots.txt | head -3
curl -s https://ваш-домен.ru/sitemap.xml | head -5
```

В `robots.txt` и `sitemap.xml` должен стоять ваш домен, а не старый:
адрес попадает туда на сборке из `NEXT_PUBLIC_SITE_URL`, которую
`docker-compose.prod.yml` передаёт из `DOMAIN`.

Дальше — руками, в браузере:

- [ ] главная открывается, замок в адресной строке на месте;
- [ ] `www.ваш-домен.ru` перебрасывает на адрес без www;
- [ ] регистрация и вход работают, письмо приходит (или ссылка видна в логе `backend`);
- [ ] вход администратором из `SUPERADMIN_EMAIL`;
- [ ] загрузка картинки в профиле сохраняется и открывается после перезагрузки;
- [ ] маршрут создаётся и остаётся после `docker compose restart`.

## 6. Резервные копии

```sh
chmod +x deploy/backup.sh
crontab -e
# добавить строку:
0 4 * * * /opt/vela/deploy/backup.sh >> /opt/vela/backups/backup.log 2>&1
```

Каждую ночь снимается дамп базы и архив загруженных файлов в `/opt/vela/backups`,
хранение — две недели. Проверить вручную: `./deploy/backup.sh`.

Восстановление базы из копии:

```sh
gunzip -c backups/vela-db-2026-08-12.sql.gz \
  | docker compose -f docker-compose.prod.yml exec -T db psql -U vela -d vela
```

## 7. Обновление

```sh
cd /opt/vela
git pull
BUILD_ID=$(date +%F-%H%M) docker compose -f docker-compose.prod.yml up -d --build
```

`BUILD_ID` обязателен. Он попадает в адрес service worker (`/sw.js?v=…`),
и по смене этого адреса браузер понимает, что появилась новая версия,
и чистит кэш предыдущей. Пересоберёте без него — часть посетителей ещё
несколько дней будет видеть старый сайт, и выглядеть это будет так,
будто обновление не выехало.

Тома с базой и файлами при пересборке не трогаются.

## 8. Переезд данных с прежней площадки

На Render уже накоплены живые данные: аккаунты, маршруты, сообщения.
Переносить нужно до того, как люди начнут ходить на новый адрес, иначе
часть данных окажется в одной базе, часть в другой.

**Переменные окружения — сначала.** Значения секретов есть только в панели
Render (`sync: false` в `render.yaml` означает, что в репозитории их нет).
Выпишите их из Dashboard → сервис `vela-api` → Environment в свой `.env`
до переезда. Особенно эти три — без них сайт продолжит работать, но
перестанет зарабатывать, и заметить это можно не сразу:

| Переменная | Что отвалится, если забыть |
|---|---|
| `TRAVELPAYOUTS_TOKEN` | реальные цены авиабилетов в блоке «Перелёт и даты» |
| `TRAVELPAYOUTS_MARKER` | партнёрская комиссия с бронирований и трансферов |
| `KIWITAXI_WL_URL` | виджет заказа трансфера прямо на странице логистики |

Полный список того, что читает код, — в `.env.prod.example`; он сверен
с `render.yaml` и с `process.env` в исходниках.

**База.** Один скрипт делает всё: снимает дамп с Render, кладёт копию
в `backups/` и заливает в локальный Postgres.

```sh
# Render → Dashboard → база vela-db → Connections → External Database URL
./deploy/migrate-from-render.sh "postgresql://user:pass@host/vela_db"
```

Внутренняя строка подключения (`internal`) снаружи не работает — нужна
именно внешняя. Скрипт запускает `pg_dump` внутри образа `postgres:16`,
чтобы версия совпала с сервером: системный `pg_dump` обычно старше
и отказывается снимать дамп.

Скрипт можно прогонять повторно — например, снять свежий дамп перед самым
переключением DNS. Каждый прогон полностью заменяет содержимое локальной базы.

**Файлы пользователей.** На бесплатном тарифе Render диск не постоянный:
загруженные картинки пропадают при каждом перезапуске сервиса. Скорее всего
переносить нечего — проверьте `/uploads` на работающем сайте. Если что-то
уцелело, скопируйте в том:

```sh
docker compose -f docker-compose.prod.yml cp ./uploads-from-render/. backend:/app/uploads/
```

**Переключение.**

1. Прогнать скрипт переноса, поднять стек, проверить сайт по IP или
   временному адресу;
2. переключить A-записи домена на новый сервер;
3. дождаться, пока разойдётся DNS, и убедиться, что сайт открывается
   и данные на месте;
4. снять домены с сервиса на Render, но **сам сервис пока не удалять** —
   пусть постоит неделю как запасной вариант.

## Что осталось от прежних схем

`render.yaml`, `frontend/netlify.toml`, `docs/DEPLOY_FREE.md`,
`docs/DEPLOY_NETLIFY.md` и `docs/DEPLOY_RU.md` описывают развёртывание
на облачных площадках. Они не удалены намеренно: пока боевая версия работает
на Render, это рабочая запасная схема. Удалять их стоит после того, как
выделенный сервер отработает без нареканий.

Ещё одна мелочь: `frontend/Dockerfile` принимает `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY`,
но в коде эта переменная нигде не читается — остаток от прежней версии карт.
Заполнять её не нужно.
